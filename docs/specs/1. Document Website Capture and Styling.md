# 1. Document Website Capture and Styling

Design spec for the next round of `document-website` changes. Written 2026-11-04 after a test run on a signed-in admin dashboard (Mambo QA, `https://emma.vigilixqa.net/`).

## Why

The first real run worked, but it showed five gaps:

1. **Full-page capture silently fails on app-shell layouts.** Mambo fixes the page to the window height and scrolls only the content pane under the breadcrumb (on purpose, so the breadcrumb stays visible). Playwright's `fullPage=true` measures the document, which never scrolls, so the "full page" image is one window tall. Most admin dashboards and SPAs are built this way.
2. **No way to make the tutorial look like the company's documents.** The `.docx` always uses python-docx's blank default. The owner wants to hand the skill a Word template, or a Word/PDF document to use as a reference.
3. **No PDF output.** The owner wants to pick one output type per run: Word, HTML, or PDF.
4. **Marker colors are hardcoded red.** Every marker can override its color, but there is no run-wide default or reusable style, and nothing stops a red marker on an orange header (exactly what happened in Step 1 of the test, where the "1" circle was hard to see).
5. **Browser mode is not configurable through the plugin.** The owner believed they had set `--headless --isolated`, but neither registered Playwright server (the official `playwright` plugin and this repo's `essential-skills` plugin) passes any option, so a window opened and the Chrome sign-in did not carry over.

## Goals

- Full-page screenshots work on pages whose content scrolls inside a box, without stitching.
- One output file per run, type chosen by the user: `.docx`, `.html`, `.md` (kept), or `.pdf` (new, only when asked).
- A Word document (`.docx` or `.dotx`) can be used as a **template**: the tutorial is built inside it and inherits its styles, page setup, headers, and footers.
- A Word or PDF document can be used as a **reference**: the agent copies its look (fonts, colors, sizes) and its structure and voice, without using the file itself.
- Marker colors can be set per marker, per run on the command line, or in a reusable style file, falling back to built-in defaults.
- Whatever the colors come from, `annotate.py` avoids drawing a marker that has low contrast with the screenshot under it.
- Every Playwright MCP browser mode is reachable (headed, headless, isolated, saved sign-in, the user's own Chrome through the extension, a chosen profile folder), with a documented default.

## Non-goals

- Scroll-and-stitch capture. The owner has seen it in browser extensions and does not like the result.
- Converting PDF to Word (`pdf2docx` or similar). A PDF is only ever a reference.
- Several output files from one build. If the user wants Word and HTML, the agent runs the build twice.
- Keeping a template's existing body content (cover pages, boilerplate sections). The body is cleared; only styles, page setup, headers, and footers carry over.
- Automating Word on macOS. PDF on macOS goes through LibreOffice or Chrome.
- Growing the window sideways for content that scrolls horizontally.

## Anti-goals

- A PDF produced "only when asked" means never: `.pdf` is never chosen as a default and no engine is launched unless the output path ends in `.pdf`.
- Auto-contrast must not turn a tutorial into a rainbow or silently ignore the user's colors. Every color change is reported as a warning naming the old color, the new color, and the measured contrast, and it can be turned off.
- No new required Python package. PDF conversion shells out to tools already on the machine; Word is driven through PowerShell, not `pywin32`.
- No credentials or session files in a git-tracked folder. A saved sign-in file is a live session secret.

## Current state (for the builder)

- `skills/document-website/SKILL.md`: the workflow. Full-page recipe at step 2 only hides the `<html>` scrollbar.
- `scripts/annotate.py`: `DRAWERS` dict; `DEFAULT_RED = "#E53935"`; colors read per marker by `color(m, field, default)`; markers drawn on a transparent overlay composited over the screenshot.
- `scripts/build_docx.py`: `BUILDERS` keyed by output extension; `build_docx` starts from `Document()`, hardcodes Normal at 11 pt and the caption as italic gray 9 pt; `build_html` uses an inline `HTML_STYLE`.
- `references/annotation-spec.md`: user-facing marker schema; must change together with `annotate.py`.
- `.claude-plugin/plugin.json`: registers `playwright` as `npx @playwright/mcp@latest` with no arguments.
- `.claude/skills/verify-document-website/`: verification skill with `features/` recipes; update the recipes in the same change.
- `@playwright/mcp` (checked 2026-11-04): every CLI option also reads a `PLAYWRIGHT_MCP_*` environment variable (`PLAYWRIGHT_MCP_HEADLESS`, `_ISOLATED`, `_EXTENSION`, `_STORAGE_STATE`, `_USER_DATA_DIR`, `_OUTPUT_DIR`, `_CONFIG`, `_CAPS`, `_BROWSER`, ...). Default is a headed browser with a persistent profile per workspace (`%LOCALAPPDATA%\ms-playwright\mcp-{channel}-{workspace-hash}` on Windows). `--caps=storage` adds `browser_storage_state` (save cookies and local storage to a file) and `browser_set_storage_state` (restore them at runtime).

## Design

### A. Full page when the page scrolls inside a box

Approach: make the browser window as tall as the content, then take a normal viewport screenshot. The page lays itself out the way it always does, the sticky breadcrumb appears once at the top, and marker coordinates stay plain viewport coordinates (no scroll offset math).

1. **Detect.** Before any full-page capture, the agent runs one `browser_evaluate` snippet (kept in a new reference, `references/full-page.md`, for the agent to copy). It returns:
   - whether the document itself scrolls (`document.scrollingElement.scrollHeight > innerHeight + 1`);
   - the main scroll box: among visible elements whose computed `overflow-y` is `auto`, `scroll`, or `overlay` and whose `scrollHeight > clientHeight + 1`, the one with the largest visible area (ties prefer `main` or `[role=main]`), with a short description (tag, id, classes) and its hidden height `scrollHeight - clientHeight`;
   - the other scroll boxes and their hidden heights (for example a sidebar), so the agent knows what will still be cut off.
   This does not depend on the site having a `<main>` element; `main` is only a tie-breaker.
2. **Choose.**
   - The document scrolls: use the existing full-page recipe (hide the scrollbar, `fullPage=true`).
   - A box scrolls: use the tall-window recipe below.
   - Nothing scrolls: a viewport screenshot is already the full page.
3. **Tall-window recipe.**
   1. Note the current viewport size; scroll the box to the top.
   2. `browser_resize` to the same width and `innerHeight + hidden height`.
   3. Wait for the layout to settle (`browser_wait_for` about one second), run the detection again, and grow again if content is still hidden (charts and lazy lists can grow after a resize). Stop after three rounds.
   4. Take a viewport screenshot (not `fullPage`) and measure marker positions in this same state.
   5. Resize back to the noted size before interacting with the page again.
4. **Limits.** Chromium cannot capture images taller than about 16384 px. If the needed height is larger, the agent caps it, says so, and documents the rest with element screenshots. Elements sized in `vh` units stretch with the window; the agent checks the image and mentions it if the result looks wrong.

`SKILL.md` gets a short "Page scrolls inside a box" entry in step 2 that says when to use this and points to `references/full-page.md` for the snippet and steps. The existing document-scroll recipe moves to the same reference so step 2 stays short.

### B. Output types, Word templates, references, and PDF

**Output type.** Still chosen by the `--output` extension of `build_docx.py`, one file per run: `.docx`, `.html`/`.htm`, `.md`, and new `.pdf`. In `SKILL.md`, step 1 maps the user's words to an extension ("Word" means `.docx`, "web page" means `.html`). Default stays `.docx`. `.pdf` only when the user asks for PDF.

**Word template: `--template <file.docx|.dotx>`.**
- Valid for `.docx` output and for `.pdf` output built through Word or LibreOffice. With `.html`, `.md`, or the Chrome PDF engine, the build prints a `[warn]` that the template is ignored.
- The build opens the template, removes everything in the body (paragraphs, tables, content controls) except the final section properties, then writes the tutorial. Styles, theme fonts and colors, page size, margins, headers, footers (including logos), and numbering carry over.
- `.dotx` files: python-docx refuses the template content type. The build copies the file to a temporary `.docx` and rewrites the main part's content type in `[Content_Types].xml` before opening it. (Builder: confirm python-docx's behavior first; if it opens `.dotx` directly, skip the rewrite.)
- Styles used: `Title` for the title, `Heading 2` for step headings, `Normal` for body text, `Caption` for captions. If the template does not define one of these, fall back to direct formatting (bold for a heading; the current italic gray 9 pt for a caption) and print one `[warn]` per missing style.
- The current hardcoded formatting (Normal 11 pt, caption italic gray 9 pt, red placeholder text) applies only when there is no template and no style file setting for it, so a template's styles are not overridden.

**Style file: `--style <style.json>`, `document` section.** The same file `annotate.py` reads (section C). Keys (all optional):

```json
{
  "document": {
    "font": "Segoe UI",
    "font_size": 11,
    "color": "#1F2328",
    "title":   {"font": "Segoe UI Semibold", "size": 26, "color": "#0B3D91", "bold": true, "align": "center"},
    "heading": {"size": 16, "color": "#0B3D91", "bold": true},
    "caption": {"size": 9, "color": "#666666", "italic": true},
    "page":    {"size": "letter", "margins_in": 1.0}
  }
}
```

- `.docx` and Word/LibreOffice `.pdf`: applied to the matching styles after the template is loaded, so the style file wins over the template for the properties it names. `page` is ignored when a template is given (the template's page setup wins) and the build warns.
- `.html` and Chrome `.pdf`: turned into CSS added after the built-in stylesheet.
- `.md`: ignored without a warning (Markdown has no styling).

**HTML stylesheet: `--css <file.css>`.** For `.html` (and Chrome `.pdf`) output, the file's contents are added after the built-in stylesheet and after the style-file CSS, so it wins. Ignored with a `[warn]` for other outputs.

**Reference documents.** A reference is read by the agent, not by the build. `SKILL.md` step 1 asks whether the user has a template or a reference, and a new `references/templates.md` explains the difference and the steps:
- Template (`.docx`/`.dotx`): pass it as `--template`. Exact look, empty body.
- Reference (`.docx` or `.pdf`): the agent reads it and then (1) writes a style file `document` section matching its fonts, sizes, and colors, and (2) follows its section structure and voice in `steps.json` (for example, an introduction step with no image, a prerequisites step, a troubleshooting step at the end).
- Reading a `.pdf` reference: the agent's own file reading (Claude Code's Read tool reads PDF pages as text and images).
- Reading a `.docx` reference: new script `scripts/describe_docx.py <file>` prints page size and margins, the styles actually used with their font, size, color, bold and italic, the heading outline, header and footer text, and the image count. It needs only python-docx.
- If the reference is a `.docx` and the user wants exactly its look, the agent suggests using it as `--template` instead.

**PDF output: `--pdf-engine auto|word|libreoffice|chrome`.**
- `word` (Windows only): build the `.docx` to a temporary file, then run PowerShell to automate `Word.Application` (invisible, alerts off): open read-only, `ExportAsFixedFormat` to PDF, close without saving, quit. Kill Word if it hangs past a timeout. Word renders templates exactly, which is why it comes first.
- `libreoffice`: build the `.docx` to a temporary file, then `soffice --headless --convert-to pdf --outdir <dir> <file>`. Found as `soffice` on PATH or in the usual install folders.
- `chrome`: build the `.html` to a temporary file, then run Chrome or Edge headless with `--print-to-pdf` and no header or footer. Found in the usual install folders (Edge ships with Windows). Templates do not apply.
- `auto` (default): `word` if Word is installed on Windows, else `libreoffice` if found, else `chrome` if found.
- No engine available: exit `2` before writing anything, listing what was looked for and how to get one. Engine failed: exit `1` with its error output.
- Temporary files are removed after conversion unless the build fails, in which case their paths are printed.

### C. Annotation colors and contrast

**Where colors come from.** For each marker field (`color`, `bg`, `fg`, and any other default-able field), first match wins:
1. the field on the marker itself;
2. command-line options on `annotate.py`: `--color` (arrows and boxes), `--bg` and `--fg` (circles and labels);
3. the style file (`--style <style.json>`, `markers` section): first the per-type block (`markers.circle.radius`), then `markers.defaults`;
4. built-in defaults (red `#E53935`, white text).

Style file `markers` section:

```json
{
  "markers": {
    "defaults": {"color": "#1565C0", "bg": "#1565C0", "fg": "#FFFFFF"},
    "circle":   {"radius": 14},
    "arrow":    {"width": 5},
    "auto_contrast": true,
    "min_contrast": 3.0,
    "palette": ["#1565C0", "#E53935", "#FDD835", "#000000", "#FFFFFF"]
  }
}
```

Per-type blocks accept any field that marker type accepts except positions and text (`to`, `from`, `at`, `rect`, `label`, `text`). Unknown keys get a `[warn]`; invalid values are an exit-`2` error naming the style file, like an invalid marker.

**Auto-contrast (on by default).**
- For each marker, sample the original screenshot (not other markers) where the marker's color will sit: along an arrow's shaft and head; a band a few pixels wide around a box's outline; a ring just outside a circle's edge; the area just around a label's pill.
- Compute the WCAG contrast ratio between the marker color and every sampled pixel and take a low percentile (around the 20th), so the marker stands out against most of what is under it, not just the average.
- If that is below `min_contrast` (default `3.0`, the WCAG minimum for graphics), pick a replacement: the first color in the style file's `palette`, then the built-in palette, that reaches the threshold; if none does, the one with the highest score. The built-in palette must include a very dark and a very light color, so a passing choice always exists.
- Not plain color inversion: inverting a mid-gray background gives mid-gray. The palette search is what the owner's "inverted or high-contrast color" asks for.
- Text inside circles and labels: after the fill is settled, if `fg` against the fill is below 3.0 (WCAG minimum for large text; marker text is bold and large), use black or white, whichever contrasts more. (Owner decision 2026-11-04, replacing 4.5: the built-in white on `#E53935` is 4.23:1, so 4.5 would flip every default marker's text to black.)
- Each change prints `[warn] marker 1 (circle): bg #E53935 has 1.6:1 contrast on the background; drew #000000 instead (8.2:1).` and the run still exits `0`.
- Off switches: `--no-auto-contrast`, `"auto_contrast": false` in the style file, or `"auto_contrast": false` on a single marker.
- Each marker is decided on its own (the builder's call, not the owner's). Because the palette order is fixed, markers on similar backgrounds get the same replacement.

**Documentation.** `references/annotation-spec.md` gets the precedence order, the auto-contrast rules, and the new options. A new `references/style-file.md` holds one complete example covering both sections (`markers` and `document`) and explains each key. `SKILL.md` points to it from steps 4 and 5. The README's skill section links to it.

### D. Browser modes and sign-in

**Default: unchanged.** Headed browser with Playwright's persistent profile per project. The user signs in once in the Playwright window and stays signed in on later runs in the same project. Recommended over isolated or extension as the default because it needs no setup and survives restarts.

**Opt-in modes**, documented in a new `references/browser-modes.md` with the exact setting for each:

| Mode | Setting | Notes |
|---|---|---|
| Headless | `PLAYWRIGHT_MCP_HEADLESS=true` | No window, so no interactive sign-in. Pair with a saved sign-in or a profile already signed in. |
| Isolated | `PLAYWRIGHT_MCP_ISOLATED=true` | Clean browser each session; nothing kept. |
| Saved sign-in at start | `PLAYWRIGHT_MCP_STORAGE_STATE=<file>` (with isolated) | Loads cookies and local storage from a file saved earlier. |
| User's own Chrome or Edge | `PLAYWRIGHT_MCP_EXTENSION=true` | Needs the Playwright extension in that browser; drives real tabs with the real sign-in. `PLAYWRIGHT_MCP_PROFILE_DIR_NAME` picks the profile. |
| Chosen profile folder | `PLAYWRIGHT_MCP_USER_DATA_DIR=<dir>` | Persistent profile in a known place. |
| Browser | `PLAYWRIGHT_MCP_BROWSER=chrome\|msedge\|firefox\|webkit` | |
| Output folder | `PLAYWRIGHT_MCP_OUTPUT_DIR=<dir>` | Where page snapshots and logs go instead of `.playwright-mcp/`. |
| Several at once | `PLAYWRIGHT_MCP_CONFIG=<file.json>` | Playwright MCP's own config file. |

- The environment variables are set in the shell before starting the agent, or in Claude Code's `settings.json` `env` block. (Builder: confirm that MCP servers started by Claude Code inherit the `settings.json` `env` values; if they do not, document the shell route only.)
- The mode is fixed when the server starts. Changing it means restarting the server (`/mcp`, reconnect) or starting a new session. The skill says this instead of pretending to switch.
- **Per-request choices without a restart:**
  - *Saved sign-in.* The plugin turns on `--caps=storage`. After the user signs in, the agent can save the sign-in with `browser_storage_state` to a file in the project's ignored temp folder (never a tracked folder; the agent warns that the file is a live session secret). Later, in any mode including headless, `browser_set_storage_state` restores it. This is the headless sign-in story.
  - *Own Chrome.* The user may register a second server with the extension option (for example `claude mcp add playwright-chrome -- npx @playwright/mcp@latest --extension`). When the user asks to "use my Chrome," the skill uses that server's tools; if it is not registered, the skill gives the one-line setup instead of guessing.
- **Plugin change.** `plugin.json` turns on the storage capability for its `playwright` server while still letting the user's `PLAYWRIGHT_MCP_CAPS` win. Preferred form: `"env": {"PLAYWRIGHT_MCP_CAPS": "${PLAYWRIGHT_MCP_CAPS:-storage}"}`. (Builder: confirm that plugin MCP config expands `${VAR:-default}`. If it does not, pass `--caps=storage` as an argument and document that this overrides `PLAYWRIGHT_MCP_CAPS`.) Bump the plugin `version`.
- **Two Playwright servers.** If both the official `playwright` plugin and this plugin are enabled, two browsers can be driven and settings applied to one do not reach the other. The README and `references/browser-modes.md` say to keep one enabled. The skill works with whichever Playwright server the session has.
- **`SKILL.md` sign-in step.** When a page needs sign-in: in headed mode, ask the user to sign in in the Playwright window and wait; offer to save the sign-in for later headless runs. In headless mode without a saved sign-in, stop and explain the options.
- **Playwright's own files.** `SKILL.md` keeps its advice to ignore `.playwright-mcp/` in git, adds `PLAYWRIGHT_MCP_OUTPUT_DIR` as the cleaner option, and tells the agent not to move that folder by hand.

## Constraints

- Python scripts stay standalone CLIs with the existing exit-code contract: `0` saved, `1` saved with problems or could not write, `2` invalid input and nothing written.
- No new required Python package. `requirements.txt` changes only if the builder finds one is unavoidable, and then `SKILL.md`'s Dependencies table and the README's Requirements section change with it.
- Script paths in `SKILL.md` use `<skill-dir>`. `SKILL.md` stays short; detail goes in `references/`.
- US English in all docs and messages.
- Every behavior change gets a matching recipe in `.claude/skills/verify-document-website/features/`, and the verification skill passes at the end.
- Generated test files go in `!tmp/` or the session scratchpad, never in tracked folders.

## Calls made without the owner

The owner said "go ahead" instead of answering the last question, so these are the author's calls:

- How the browser mode is chosen: set once by environment variables or a Playwright config file, plus two per-request options that need no restart (saved sign-in through `--caps=storage`, and an optional second server for the user's own Chrome).
- Default browser mode stays headed with a persistent profile.
- PDF engine order is Word, then LibreOffice, then Chrome.
- One style file shared by both scripts, with `markers` and `document` sections.
- Command-line colors win over the style file (the usual convention: the most specific, most recent setting wins).
- Auto-contrast decides per marker, not per image.
- The template body is cleared, not preserved.
